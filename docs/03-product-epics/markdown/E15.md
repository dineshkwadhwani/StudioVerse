## 1. Document Purpose

This epic defines the notification framework for StudioVerse Coaching Studio. It covers all email notification opportunities across authentication, onboarding, assignments, cohorts, approvals, wallet and coin flows, referral lifecycle, Bot Hero requests, promotion requests, and high-priority admin alerts.

The purpose of this epic is to make sure users, creators, and administrators receive the right communication at the right moment, while allowing Super Admin to turn notification streams on or off per tenant.

---

## 2. Epic Objective

The objective of Epic E15 is to deliver a configurable notification system that can:

- Welcome newly registered users.
- Notify users when activities are assigned, updated, completed, or cancelled.
- Notify users when they are added to or removed from cohorts.
- Notify requesters when approvals are submitted, approved, or denied.
- Notify creators and operators about wallet, cash-out, referral, and Bot Hero workflows.
- Alert Super Admins about new high-priority requests.
- Respect tenant-level notification toggles before sending any email.

---

## 3. Business Context

StudioVerse already includes onboarding, assignment, wallet, referral, cohort, and approval workflows. Those workflows create important state changes that should be communicated through email so users are not left guessing.

Notification control must remain centralized. Each tenant should have its own notification settings in Manage Notifications, and Super Admin should be able to enable or disable each notification type before any email is sent.

## 4. Scope

### 4.1 In Scope

This epic includes:

- Email notifications for onboarding and authentication flows.
- Email notifications for assignment lifecycle events.
- Email notifications for cohort membership changes.
- Email notifications for promotion request lifecycle.
- Email notifications for Bot Hero request lifecycle.
- Email notifications for wallet and coin request lifecycle.
- Email notifications for cash-out request lifecycle.

This epic does not include:

- Push notifications.
- SMS or WhatsApp notifications.
- In-app notification center.

- Template editor.

---

## 5. Notification Principles

- Every important user-facing state change should be evaluated for email notification.
- Notification behavior must be role-aware and tenant-aware.
- Notification settings must be controlled by Super Admin on a per-tenant basis.
- Notifications must only send when the corresponding toggle is enabled.
- Notifications should be auditable and traceable back to the source event.

## 6. Notification Domains

### 6.1 Authentication and Onboarding

- User self-registers via AuthWizard, send welcome email with role confirmation.
- User is automatically provisioned during assignment, send welcome and activation email.
- Managed user is created by coach or company, send welcome email inviting profile setup.
- Registration bonus coins are issued, send informational notice to the new user.

### 6.2 Assignments

- Activity assigned to a user, send assignment email.
- Activity assigned to all members of a cohort, send per-member assignment email.
- Assignment changes to in_progress, send optional nudge or confirmation.
- Assignment marked completed, send completion confirmation to assignee and optional notice to assigner.
- Assignment cancelled, send cancellation notice to assignee.
- Recommendation created for a user, send recommendation notice where applicable.

### 6.3 Cohorts

- User added as a member of a cohort, send welcome to cohort email.
- User removed from a cohort, send removal notice.
- Cohort membership updated in bulk, send member-specific update email when needed.

### 6.4 Promotion Requests

- Promotion request submitted for a program, event, or assessment, send acknowledgment to requester.
- Promotion request approved by Super Admin, send approval notice to requester.
- Promotion request denied by Super Admin, send denial notice with reason to requester.

### 6.5 Bot Hero Requests

- Bot Hero request submitted, send acknowledgment to requester.
- Bot Hero request approved, send approval notice with start and end dates.
- Bot Hero request denied, send denial notice with reason.
- Bot Hero period ending soon, send advance expiry reminder to the professional.

### 6.6 Wallet and Coins

- Coin request submitted by professional, send acknowledgment to requester.
- Coin request approved by company, send approval notice with coin amount.
- Coin request denied by company, send denial notice.
- Registration bonus coins issued, send informational notice to the new user.
- Cash-out request submitted, send acknowledgment to requester.
- Cash-out request approved by Super Admin, send approval notice with payout details.
- Cash-out request denied by Super Admin, send denial notice with reason.

### 6.7 Referrals

- Referral invite sent, send invite email.
- Referral reminder sent, send reminder email.
- Referred user joins the platform, send confirmation to the referrer and mark referral as credited.

### 6.8 Admin Alerts

- New cash-out request submitted, alert Super Admin.
- New Bot Hero request submitted, alert Super Admin.
- New promotion request submitted, alert Super Admin.

## 7. Functional Requirements

### 7.1 Email Notification Engine

The platform must evaluate workflow events and determine whether an email should be sent.

**Requirements**

- Notification triggers must be driven from backend workflow events.
- Notification routing must map events to templates and recipients.
- Notification logic must respect tenant-level enable/disable settings.
- Notification delivery must be blocked when the tenant toggle is disabled.
- Notification events must be logged for audit purposes.

**Acceptance criteria**

- Relevant workflow events can trigger email notifications.
- Disabled notification types do not send.
- Enabled notification types do send.
- Event-to-template mapping is deterministic.

### 7.2 Tenant Notification Settings

Each tenant must have a Manage Notifications configuration under Super Admin control.

**Requirements**

- Notification settings must be stored per tenant.
- Each notification category must have its own toggle.
- Super Admin must be able to turn each notification type on or off.
- Notification checks must run before email dispatch.
- If a notification type is disabled, the workflow may continue but no email is sent.

**Acceptance criteria**

- Super Admin can manage notification toggles per tenant.
- Notification sending respects the toggle state.
- One tenant’s settings do not affect another tenant.

### 7.3 Onboarding Notifications

The platform must notify users during account creation and activation.

**Requirements**

- Send welcome email for self-registration.
- Send welcome/activation email for auto-provisioned users.
- Send welcome email for coach/company-created users.
- Send onboarding bonus notification when coins are issued at registration.

**Acceptance criteria**

- Every supported onboarding path has a matching email opportunity.
- User receives the correct welcome email for their entry path.

### 7.4 Assignment Notifications

The platform must notify users when activities are assigned or change status.

**Requirements**

- Send assignment email on individual assignment.
- Send per-member email when cohort assignment applies.
- Send optional email when assignment moves to in_progress.
- Send completion email when assignment is completed.
- Send cancellation email when assignment is cancelled.

**Acceptance criteria**

- Assignment-related state changes are notify-able.
- Cohort assignment can notify each affected member.

### 7.5 Cohort Notifications

The platform must notify users about cohort membership changes.

**Requirements**

- Send email when a user is added to a cohort.
- Send email when a user is removed from a cohort.
- Support cohort-level bulk updates where members need individual notifications.

**Acceptance criteria**

- Cohort membership changes can generate emails.
- Notifications are sent to the correct cohort member.

### 7.6 Approval Notifications

The platform must notify requesters when approval workflows are resolved.

**Requirements**

- Send acknowledgment when a promotion request is submitted.
- Send approval email when a promotion request is approved.
- Send denial email with reason when a promotion request is denied.
- Send acknowledgment when a Bot Hero request is submitted.
- Send approval email with date range when a Bot Hero request is approved.
- Send denial email with reason when a Bot Hero request is denied.

**Acceptance criteria**

- Approval workflows produce the correct sender and recipient behavior.
- Denial emails include the reason where available.

### 7.7 Wallet Notifications

The platform must notify users about coin and cash-out workflows.

**Requirements**

- Send acknowledgment when coin request is submitted.
- Send approval or denial when coin request is resolved.
- Send informational notice when registration bonus coins are credited.
- Send acknowledgment when cash-out request is submitted.
- Send approval or denial email for cash-out requests.

**Acceptance criteria**

- Coin and cash-out events can generate email notifications.
- Users receive relevant financial workflow updates.

### 7.8 Referral Notifications

The platform must notify referrers and referred users where applicable.

**Requirements**

- Send referral invite when invite is created.
- Send reminder when invite remains pending.
- Send referrer confirmation when the referred user joins.
- Ensure referral join does not duplicate onboarding credit logic.

**Acceptance criteria**

- Referral lifecycle emails can be sent.
- Referral join confirmation goes to the correct referrer.

### 7.9 Admin Alert Notifications

The platform must support internal alert emails for Super Admin.

**Requirements**

- Send alert email for new cash-out request.
- Send alert email for new Bot Hero request.
- Send alert email for new promotion request.
- Alerts should only go to authorized administrative recipients.

**Acceptance criteria**

- Super Admin can be alerted for new high-priority requests.
- Alerts are limited to correct admin audiences.

## 10. Technical Constraints

- Notification dispatch must run through backend services or trusted functions.
- UI must not send email directly.
- Notification checks must run before dispatch.
- Super Admin settings must be tenant-scoped.
- Notification logs must store event name, recipient, tenant, and send status.
- Template content should be role-aware and tenant-aware.

---

## 11. Non-Functional Requirements

- Notifications must be deterministic and auditable.
- Notification gating must be fast and reliable.
- Notification sending must not block core user workflows.
- Disabled notification types must not produce side effects.
- Notification logic must be safe across all StudioVerse tenants.
- Email content must be clear and role-specific.

---

## 12. Risks and Mitigations

1. Duplicate notification sends  
Mitigation: use idempotent notification event keys.

2. Missing tenant settings  
Mitigation: provide safe defaults and fail closed for sensitive categories.

3. Incorrect recipient targeting  
Mitigation: resolve recipient through validated backend workflow context.

4. Notification noise  
Mitigation: keep categories granular and toggles tenant-scoped.

5. Sensitive alerts going to the wrong audience  
Mitigation: separate user-facing templates from admin alert templates.

## 14. Glossary

- **Notification Type:** A category of email event such as assignment, approval, or referral.
- **Tenant Notification Settings:** Per-tenant toggles that control whether a notification type can be sent.
- **Manage Notifications:** Super Admin screen for enabling or disabling notification categories.
- **Template:** Standard email format used for a notification category.
- **Notification Log:** Audit record of a notification event and its delivery outcome.
