# TITLE StudioVerse - EPIC E18 - Development Plans

This Epic defines the Development Plan module for StudioVerse. The module enables an Individual to create one or more personal development plans, define development objectives against the platform competency framework, receive system recommendations for relevant Programs, Events, and Assessments, finalize the plan by assigning selected tasks, and then track progress over time.

The module also supports Coach-created plans for Coachees and Company-created plans for Individuals or Coachees. Development Plans are tenant-gated and will only appear when the tenant configuration explicitly enables the feature.

Current constraints:

- Pending invitation targets are selectable through managed-user data, but plan finalization still assumes the subject can receive direct assignment records immediately. Invite-only target handling needs an explicit follow-up decision.

# TITLE StudioVerse - 1. Purpose

StudioVerse already provides learning content, assessments, credits, and a structured competency framework. What is missing is a guided planning layer that transforms platform content into a measurable development journey.

The purpose of this Epic is to enable:
- structured personal development planning,
- coach-guided development planning,
- company-sponsored development planning,
- objective definition using Categories, SubCategories, and Topics,
- intelligent task recommendations from StudioVerse content,
- credit-based plan finalization,
- and progress tracking against assigned development tasks.

This module closes the loop between intent, action, and measurable progress.

---

# TITLE StudioVerse - 2. Business Context

Users currently consume Programs, Events, and Assessments in a fragmented way. There is no formal mechanism to say what a person wants to develop, which platform items support that goal, how much the journey will cost, and how progress will be tracked.

The Development Plan module creates a structured growth path. It links the competency framework to the learning library and uses the wallet economy to make plan creation meaningful. It also gives Coaches and Companies a simple way to create and monitor development plans for their coachees or team members.

# TITLE StudioVerse - 4. Core Concept

Every Individual can have one subject-level set of Development Objectives and one or more Development Plans built from those objectives.

The first Development Plan may be free, depending on tenant configuration. Subsequent plans require credits. The free plan count is configured per tenant. The cost per plan is also configured per tenant.

Plan pricing works in two layers:
1. Plan entitlement pricing: how many plans are free.
2. Plan constituent pricing: the cost of the tasks selected into a plan.

Creating or updating Development Objectives is separate from creating a Development Plan shell. A new plan is created from the Development Plan tab and snapshots the current subject objectives into the plan so the plan retains its original planning context even if the subject objectives change later.

Creating a plan shell is not the same as paying for the plan contents. When the user finalizes the plan, the system calculates the total credit cost of all selected tasks and shows the total for confirmation. Once confirmed, the wallet is charged and the tasks become assigned tasks.

Example: if the user adds a task worth 4 credits, that 4-credit charge is applied when the plan is finalized.

# TITLE StudioVerse - 6. Tenant Configuration

The Development Plan module is controlled by a new Development section in tenant configuration.

## 6.1 Configuration Fields

- `developmentPlan.enabled`
  - Boolean flag.
  - If `true`, the module becomes available to the tenant.
  - If `false`, the Development Plan item is hidden from the Action menu group.

- `developmentPlan.freePlanCount`
  - Number of free plans allowed per Individual.
  - Default behavior should be explicitly set by tenant configuration.

- `developmentPlan.costPerPlan`
  - Credit cost of a plan beyond the free entitlement.
  - Used when a user has exhausted free plan availability.

- `developmentPlan.competencyLegend`
  - Array or table describing the proficiency levels available for objective selection.
  - Displayed in the Objectives tab as the legend table.

## 6.2 Visibility Rule

If the feature flag is disabled, users must not see the Development Plan action.
If the feature flag is enabled, eligible users must see a Development Plan item in the Action menu group.

# TITLE StudioVerse - 9. Pricing and Credit Rules

## 9.1 Free Plan Rule

Each Individual receives the number of free Development Plans configured by the tenant.
A plan within that free entitlement does not require a plan access charge.

## 9.2 Plan Constituent Rule

The actual plan charge is the total cost of the selected plan constituents.
If the user selects tasks worth 4 credits total, the finalization step charges 4 credits.

## 9.3 Finalization Rule

Plan creation is only completed when the user confirms the credit total.
The system must clearly display:
- the target person,
- the selected items,
- the total credits required,
- and the confirmation message before finalization.

## 9.4 Wallet Actor Rule

- If an Individual creates a plan for self, the Individual pays.
- If a Coach creates a plan for a Coachee, the Coach pays.
- If a Company creates a plan for an Individual or Coachee, the Company pays.

# TITLE StudioVerse - 10. Three-Tab Experience

Every Development Plan has three tabs:
- Objectives
- Development Plan
- Track Plan

## 10.1 Objectives Tab

The Objectives tab is used to define what the Individual wants to develop.

It shows:
- all Categories as the top-level competency list,
- SubCategories when a Category is selected,
- Topics when a SubCategory is selected,
- a dropdown for desired skill level for each selected SubCategory and Topic,
- a legend table at the bottom, driven by tenant configuration.

The user may define one or more objectives across the competency framework.

## 10.2 Development Plan Tab

This tab becomes available only after objectives have been set.

The system uses the selected objectives to search relevant:
- Programs,
- Events,
- Assessments.

Recommendation logic:
- Topic match first.
- If no Topic match exists, use SubCategory match.
- If no SubCategory match exists, use Category match as fallback.

Each recommended item must show:
- a checkbox,
- resource name,
- resource type,
- credit cost,
- a complete-by date field when selected.

After the user selects items, the system calculates the total credits and shows a confirmation screen before plan creation.

## 10.3 Track Plan Tab

This tab becomes available only when the plan has at least one active task.

It shows:
- overall summary at the top,
- total tasks,
- completed tasks,
- pending tasks,
- overdue tasks,
- task status against each assigned item,
- launch button for each task.

Overdue tasks must be clearly marked as overdue.

# TITLE StudioVerse - 11. Objective Setting Logic

The Objective flow must follow this hierarchy:
1. User selects a Category / Competency.
2. System lists the available SubCategories / Skills.
3. User selects a SubCategory / Skill.
4. System lists the Topics for that Skill.
5. User selects one or more Topics.
6. User selects a desired development level for the SubCategory and Topic.

The legend table displayed at the bottom must come from tenant configuration.

The design should support objective setting with or without Topics, depending on the completeness of the content taxonomy.

---

# TITLE StudioVerse - 12. Recommendation Engine

The recommendation engine must match selected objectives to content using the platform taxonomy.

Matching order:
1. Topic-level match.
2. SubCategory-level match.
3. Category-level match.

For every objective, the engine should search:
- Programs,
- Events,
- Assessments.

The engine should:
- deduplicate results,
- prioritize stronger matches,
- keep results relevant to the target development objective,
- allow the user to manually select items from the recommendation list.

If no Topic match exists, the system should still recommend Category-level development items to ensure the plan can be completed.

---

# TITLE StudioVerse - 13. Plan Finalization Flow

When the user clicks Create Plan:
1. The system totals the credit cost of selected items.
2. The user sees a final confirmation dialog.
3. The confirmation dialog shows the selected items and total credits.
4. The dialog states that the items will be assigned to the target Individual.
5. When confirmed, the plan is created.
6. All selected items become assigned tasks.
7. The payer wallet is charged.
8. The Track Plan tab becomes available.

If the user cancels, no plan is created and no credit is charged.

# TITLE StudioVerse - 18. Non-Functional Requirements

- Tenant isolation must be preserved.
- Role-based access must be enforced.
- All plan creation and credit debits must be server-side.
- Recommendation queries must be performant and indexed.
- Wallet transactions must be idempotent.
- Partial failures must not leave the system in an inconsistent state.
- The UI must remain responsive even if recommendation results are large.
- Feature visibility must be controlled solely by tenant configuration.

# TITLE StudioVerse - 20. Risks and Mitigations

1. Recommendation results are irrelevant.  
   Mitigation: use topic-first matching and relevance ordering.

2. Duplicate credit debit on repeated confirmation.  
   Mitigation: use idempotent plan finalization.

3. Insufficient wallet balance.  
   Mitigation: pre-check balance before confirmation.

4. Missing competency legend.  
   Mitigation: provide a default fallback legend.

5. Feature visible in the wrong tenant.  
   Mitigation: hard-gate the feature on tenant config.

6. Plan created without tasks due to partial failure.  
   Mitigation: perform create and debit within atomic server-side logic where possible.
