# StudioVerse

## Functional Specification Document

## Search and Messaging

**Epic ID:** E16  
**Document Version:** 1.0  
**Date:** May 2026  
**Classification:** Confidential  
**Prepared For:** Product, Design, Engineering, and Stakeholder Review

---

## 1. Document Purpose

This document defines Epic E16 for the StudioVerse platform. It covers the Search capability and the associated Messaging capability introduced to support lead discovery, lead unlock, and coach-to-individual and individual-to-coach connection flows.

Search is a universal feature available to all authenticated users. It allows users to discover platform resources (Programs, Assessments, Events) and, based on their role, discover other users such as Coaches, Coaching Companies, or Individuals.

The Messaging capability is introduced alongside Search as a direct outcome of lead discovery. Coaches and Companies can send structured Intro Messages to unlocked leads. Individuals can send Intro Messages to Coaches and Companies they discover. All messages are stored and accessible through a new Messages section in the navigation.

This epic is a revenue-generating capability in addition to a discovery capability. Lead unlocking via credit spend is the monetisation mechanism that sits at the heart of the Search and Discovery flow.

---

## 2. Epic Objective

The objective of Epic E16 is to deliver:

- A universal Search page accessible from all studio navigation menus.
- Category-based search across Programs, Assessments, Events, Coaches, Companies, and Individuals.
- Role-aware search rules governing which user types can discover which other user types.
- Association protection rules preventing discovery of users who are already associated.
- Lead tile display with locked and unlocked states for user discovery results.
- Lead unlock flow using credits from the user's wallet.
- Intro Message sending from both Coaches/Companies and Individuals.
- Persistent message storage in a Messages collection.
- A Messages page with Inbox and Outbox tabs accessible from all studio navigation menus.
- Locked message behaviour for coach/company-received intro messages, with credit-based unlock.

---

## 3. Business Context

StudioVerse is a multi-role coaching and learning platform. As the platform grows, users need a way to discover resources and connect with the right people. Without a discovery layer, the platform depends entirely on direct invitations and assignments, limiting organic growth and network effects.

Search solves three problems simultaneously:

1. **Resource discovery**: Users can find relevant Programs, Assessments, and Events they might not otherwise encounter.
2. **Professional discovery**: Individuals can find Coaches and Companies to work with. Coaches and Companies can discover unassociated Individuals who may be prospects.
3. **Monetisation**: Lead visibility and lead unlock creates a credit-spend event tied to high-intent actions, reinforcing the platform's internal economy established in E13 and E14.

The association protection rule is fundamental to the platform's trust model. StudioVerse must not allow one Coach or Company to poach another's associated users. Discovery is only permitted for unassociated users.

## 5. Actors

### 5.1 Super Admin

- Not a search user in this epic.
- May have visibility into message and lead unlock transactions through existing audit and reporting flows.

### 5.2 Company User

Can:
- Search Programs, Assessments, Events, and Individuals.
- Cannot search other Companies in this phase.
- Coaches searched must be unassociated (not already linked to another Company).
- Unlock Individual lead tiles by paying Lead Unlock Fee.
- Send Intro Message to unlocked Individuals.
- View Messages inbox and outbox.
- Unlock received Intro Messages from Individuals by paying Lead Unlock Fee.

### 5.3 Professional (Coach) User

Can:
- Search Programs, Assessments, Events, and Individuals.
- Individuals searched must be unassociated (not already linked to a Coach or Company).
- Unlock Individual lead tiles by paying Lead Unlock Fee.
- Send Intro Message to unlocked Individuals.
- View Messages inbox and outbox.
- Unlock received Intro Messages from Individuals by paying Lead Unlock Fee.

### 5.4 Individual User

Can:
- Search Programs, Assessments, Events, Coaches, and Companies.

- View Profile of any Coach or Company from search results.
- Send a single default Intro Message to any Coach or Company.
- View Messages inbox and outbox.

## 6. Search Page Specification

### 6.1 Navigation Entry Point

- Search is the first menu item in its own navigation group across all studio navigation menus.
- It is available to all authenticated users regardless of role.
- Clicking the Search menu item opens the Search page.

### 6.2 Search Page Layout

The Search page contains:

- A prominent text input field for entering the search string.
- A category selector area below the text input.
- A results area below the category selector.

### 6.3 Category Checkboxes

The following categories are shown as checkboxes below the search input:

| Category | Shown to |
|---|---|
| Programs | All roles |
| Assessments | All roles |
| Events | All roles |
| Coaches | All roles (subject to role-based result rules) |
| Companies | Individual users only |
| Individuals | Company and Professional users only |

All categories available to the current user's role are pre-selected (checked) by default.

If a user wishes to search within a specific category only, they uncheck all other categories and check only the desired one.

At least one category must be selected. If a user deselects all categories, search cannot proceed and a validation hint must guide them to select at least one.

### 6.4 Search Execution

Search is triggered when the user submits the query (Enter key or Search button).

The search string must be at least 2 characters before submission is permitted.

Search results are fetched per selected category and displayed in a unified results view. Results from all selected categories are shown together on the same page, grouped by category with category headers.

An empty result state must be shown per category section when no matches are found. The empty state must be clear and encourage the user to try different terms.

## 7. Search Matching Rules

### 7.1 Programs, Assessments, and Events

Search string is matched against the following fields:

- Name
- Short Description
- Long Description
- City (Events only)
- Delivery Type (Programs and Events only)

Matching rules:

- Only items with `visibility: public` and status `active` or `published` are returned.
- Platform-owned and creator-owned public content are both eligible.
- Private content is never returned in search results.

Result tiles for Programs, Assessments, and Events follow the same card and button pattern used on Landing pages and View All pages, adapted per the current user's role.

### 7.2 Coach and Individual Discovery (Professional and Company Role)

When a Professional or Company searches, user discovery follows these rules:

**Search fields matched:**
- Full Name
- Professional Headline
- Bio
- Credentials
- Certifications

**Association protection rule:**
- Only users who are **not associated** to any Coach or Company are returned.
- A user is considered associated if their user record has a non-null `associatedProfessionalId` or `associatedCompanyId` field.
- Associated users are never returned in search results for Professional or Company searchers, regardless of search string match.

**Lead tile state:**
- If the Lead Unlock Fee configured in monetisation settings is zero (0), the tile is shown fully unlocked.
- If the Lead Unlock Fee is greater than zero, the tile is shown in a locked state until the searching user has paid to unlock it.

### 7.3 Coach and Company Discovery (Individual Role)

When an Individual searches:

**Search fields matched:**
- Full Name
- Professional Headline
- Bio
- Credentials
- Certifications

**Association rule:**
- All Coaches and Companies are returned regardless of their association status.
- There is no association filtering for Individual searchers.

**Lead tile state:**
- Coach and Company tiles are always shown unlocked for Individual searchers.
- Lead Unlock Fee does not apply to Individual discovery of Coaches or Companies.

## 8. Lead Tile Specification

### 8.1 Locked Tile

When a user discovery result is in locked state:

- The tile displays a blurred or obscured representation of the person's identity.
- A lock icon and the text "Unlock this Lead" is shown.
- The credit cost to unlock is displayed clearly: e.g., "5 Credits to Unlock".
- An Unlock button is shown.
- Clicking Unlock initiates the Lead Unlock Flow (see Section 9).

### 8.2 Unlocked Tile

When a user discovery result is in unlocked state (either Lead Unlock Fee is zero, or the searching user has previously paid to unlock, or the current user is an Individual viewing a Coach/Company):

The tile displays:
- Profile image of the user (if available).
- Full name.
- Professional Headline.
- Activity Index (a summary count or indicator of the user's activity on the platform, such as number of programs completed or assigned).
- **View Profile** button — opens the user's full profile page.
- **Send Message** button — initiates the Intro Message flow (see Section 11).

### 8.3 Unlock Persistence

Once a searching user has paid to unlock a specific lead tile, the unlock state must persist permanently for that searching user and that lead combination.

This means:
- If the same search is run again on a future day, the previously unlocked tile must appear in the unlocked state.
- The unlock state is stored in a `leadUnlocks` collection (see Section 15).
- Unlock state must be checked on result rendering to restore unlocked tiles without requiring repeated payment.

## 9. Lead Unlock Flow

### 9.1 Trigger

The Lead Unlock Flow is initiated when a Professional or Company user clicks the Unlock button on a locked lead tile.

### 9.2 Confirmation

A confirmation modal is shown before any credit deduction occurs.

The modal must display:
- The name (partial or blurred) of the lead to be unlocked.
- The credit cost to unlock.
- The user's current available wallet balance.
- A Confirm Unlock button.
- A Cancel button.

If the user does not have sufficient credits, the modal must show a "Insufficient Credits" message and direct them to Buy Credits (link to Buy Credits page from E13).

### 9.3 Processing

On confirmation:
- Deduct the Lead Unlock Fee from the user's wallet via a wallet debit transaction.
- Write a `leadUnlocks` record for the combination of `unlockerUserId` and `leadUserId`.
- Write a wallet transaction ledger entry with reason: `Lead unlock - {Lead Name}` and type `debit`.
- Return the unlocked tile state to the UI.

### 9.4 Idempotency

The system must check for an existing `leadUnlocks` record before processing an unlock. If a record already exists, the tile must render as unlocked without charging again.

## 10. Resource Tile Specification (Programs, Assessments, Events)

Search results for Programs, Assessments, and Events follow the existing tile and button pattern used across the platform.

Tile contents:
- Cover image (if available).
- Name.
- Short description.
- Relevant metadata (e.g., delivery type for programs, city for events).
- A Find Out More button always shown.
- Role-appropriate action buttons consistent with Landing and View All page behaviour.

No locked state applies to resource tiles.

## 11. Intro Message Flow

### 11.1 Send Message — Professional or Company Sender

When a Professional or Company user clicks Send Message on an unlocked Individual lead tile:

A message composition modal appears with:
- The recipient's name shown at the top.
- Two pre-templated message options displayed for selection.
- A radio or selection interface to choose one template.
- A Send button.
- A Cancel button.

**Template 1 — Standard Introduction:**
> "Hello, I am Coach [Sender Name]. I would be glad to assist you in your development journey. Let me know if you would like to connect."

**Template 2 — Personalised Introduction:**
A message dynamically constructed using the sender's profile data:
> "Hello, I am [Sender Name], a [Professional Headline] with expertise in [top skills or credentials from profile]. I have [brief accomplishment or credential]. I believe I can support your growth journey. I would love to connect and explore how I can help."

Both templates are populated from the sender's profile fields at the time of sending. If profile fields required for Template 2 are empty, Template 2 must either show a graceful fallback or prompt the sender to complete their profile.

On send:
- The message is written to the `messages` collection with:
  - `senderId`
  - `senderName`
  - `senderRole`
  - `receiverId`
  - `receiverName`
  - `messageBody`
  - `messageType: 'intro'`
  - `status: 'sent'`
  - `unlocked: false` (default for coach/company-sent messages is that receiver sees them; but for individual-to-coach messages, receiver unlock state applies — see Section 13)
  - `createdAt`
- A success confirmation is shown inline in the modal.

### 11.2 Send Message — Individual Sender

When an Individual clicks Send Message on an unlocked Coach or Company tile:

A message composition modal appears with:
- The recipient's name shown.
- A single default message pre-populated:
> "Hi, I am [Sender Name]. I would like to connect."
- The sender's name and email are attached to the message.
- A Send button and a Cancel button.

On send:
- The message is written to the `messages` collection with the same field set as above, with `messageType: 'intro'`.
- The message is sent to the Coach or Company's inbox.
- This message arrives in a **locked state** in the Coach or Company's inbox (see Section 13).

### 11.3 Duplicate Send Prevention

A user must not be able to send more than one Intro Message to the same recipient. If an Intro Message from the current user to the same recipient already exists in the messages collection, the Send Message button must show a "Message Sent" state and clicking it again must show an appropriate informational message rather than allowing a duplicate.

## 13. Messages Page Specification

### 13.1 Page Layout

The Messages page has two tabs:
- **Inbox** — Messages received by the current user.
- **Outbox** — Messages sent by the current user.

The active tab is Inbox by default.

### 13.2 Message List Item

Each message in Inbox or Outbox shows:
- Sender name (Inbox) or Receiver name (Outbox).
- Date and time.
- First 60–80 characters of the message body as a preview.
- For locked inbox messages: a lock icon instead of the message preview.

### 13.3 Opening a Message

Clicking a message list item opens a message detail modal showing the full message.

For unlocked messages:
- Full message body is shown.
- Sender details are shown.
- Date sent is shown.

For locked messages (Coach or Company inbox only):
- The message body is hidden.
- A lock icon and "This message is locked" text is shown.
- The credit cost to unlock is shown: e.g., "Unlock for 5 Credits".
- An Unlock Message button is shown.
- Clicking Unlock Message initiates the Message Unlock Flow (Section 14).

### 13.4 Message Lock Rules

| Sender Role | Receiver Role | Lock State on Arrival |
|---|---|---|
| Individual | Professional | Locked |
| Individual | Company | Locked |
| Professional | Individual | Unlocked |
| Company | Individual | Unlocked |

Messages sent by Coaches or Companies to Individuals always arrive unlocked. Messages sent by Individuals to Coaches or Companies always arrive locked and require the receiving Coach or Company to pay Lead Unlock Fee to read the content.

---

## 14. Message Unlock Flow

### 14.1 Trigger

Initiated when a Professional or Company user clicks Unlock Message on a locked inbox message.

### 14.2 Confirmation

A confirmation modal is shown:
- Identifies that the message is from an Individual.
- Shows credit cost to unlock.
- Shows user's available wallet balance.
- Confirm Unlock and Cancel buttons.
- Insufficient credits message with link to Buy Credits if balance is too low.

### 14.3 Processing

On confirmation:
- Deduct Lead Unlock Fee from the receiver's wallet.
- Update the `messages` document to set `unlocked: true` and `unlockedAt` timestamp.
- Write a wallet transaction ledger entry: reason `Message unlock - Intro message from {Sender Name}`, type `debit`.
- Return the full message body in the UI.

### 14.4 Persistence

Once a message is unlocked, it remains unlocked permanently for the receiver. The `unlocked: true` flag persists on the message record. Re-opening the message on future visits must not re-prompt for unlock.

## 15. Data Model

### 15.1 New Collections

**leadUnlocks**

Stores the persistent unlock state between a searching user and a lead.

| Field | Type | Description |
|---|---|---|
| `id` | string | Auto-generated document ID |
| `unlockerUserId` | string | User ID of the person who paid to unlock |
| `leadUserId` | string | User ID of the lead that was unlocked |
| `studioType` | string | Studio context at time of unlock |
| `tenantId` | string | Tenant at time of unlock |
| `creditsCharged` | number | Credits deducted for this unlock |
| `walletTransactionId` | string | Reference to wallet transaction ledger entry |
| `unlockedAt` | timestamp | When unlock occurred |

**messages**

Stores all Intro Messages sent through the platform.

| Field | Type | Description |
|---|---|---|
| `id` | string | Auto-generated document ID |
| `senderId` | string | User ID of the sender |
| `senderName` | string | Display name of sender at time of send |
| `senderRole` | string | Role of sender: professional, company, individual |
| `receiverId` | string | User ID of the receiver |
| `receiverName` | string | Display name of receiver at time of send |
| `messageBody` | string | Full message text |
| `messageType` | string | Always `intro` in this epic |
| `templateUsed` | string | `template_1`, `template_2`, or `individual_default` |
| `studioType` | string | Studio context |
| `tenantId` | string | Tenant context |
| `status` | string | `sent` |
| `unlocked` | boolean | Whether receiver has unlocked this message |
| `unlockedAt` | timestamp | When receiver unlocked (null if not yet) |
| `walletTransactionId` | string | Wallet transaction reference if unlock occurred |
| `createdAt` | timestamp | Message creation time |

### 15.2 Extensions to Existing Collections

**walletTransactions** (existing)

New transaction reasons introduced in this epic:
- `Lead unlock - {Lead Name}` — type: `debit`
- `Message unlock - Intro message from {Sender Name}` — type: `debit`

**users** (existing)

No schema changes required. Association fields `associatedProfessionalId` and `associatedCompanyId` are already expected from prior epics and are read by search filtering logic.

### 15.3 Monetisation Config Reference

This epic reads the following value from the monetisation configuration (established in E14):
- `leadUnlockFee` — the credit cost to unlock a lead tile or a locked message. This is a single configurable value managed by Super Admin.

## 19. Non-Functional Requirements

- Search query execution must be performed through the service layer. No direct Firestore queries from components.
- Lead unlock and message unlock must use Firebase Functions for wallet debit operations (trusted server-side logic).
- All credit deductions must be atomic and idempotent.
- No sensitive user data must be exposed in locked tile or locked message states.
- Association filtering must happen server-side or at the service layer, not by rendering and then hiding results client-side.
- Studio type scoping must be applied to all collection reads.
- Role-based access enforcement must be applied at service and Firestore rules level.
- Messages collection must be secured so users can only read their own sent or received messages.
- leadUnlocks collection must be secured so only the unlocking user can create their own records.

## 21. Risks and Mitigations

1. **Association data not consistently populated across users**  
   Mitigation: Treat null or missing association fields as "unassociated". Document field expectation clearly in the user schema for prior epic alignment.

2. **Search performance on large datasets**  
   Mitigation: Firestore does not support full-text search natively. For this phase, client-side filtering on fetched results per category is acceptable. Future phase should integrate Algolia or Typesense for scalable search.

3. **Template 2 message quality depends on profile completeness**  
   Mitigation: If required profile fields are empty, fall back to Template 1 or display an inline prompt to complete profile before sending.

4. **Duplicate unlock payment due to race condition**  
   Mitigation: Idempotency check on `leadUnlocks` record existence before processing. Atomic write using Firestore transaction.

5. **Credit balance race condition on concurrent unlock actions**  
   Mitigation: Wallet debit must use Firebase Function with Firestore transaction to prevent double-spend.

6. **Search returning associated users incorrectly**  
   Mitigation: Association filter applied at service layer using Firestore where clauses. Add QA test specifically for this rule.
